创建日期：2026-10-11（Asia/Shanghai）。

状态：P0 工程实现已完成（2026-10-11），离线协议验证通过；真实模型验收结果见 4.6。P1–P4 尚未实施，本次按用户选择先完成并验证 P0。

## 2. 范围及必须保持的行为

本轮计划覆盖：

1. 文件／目录对象的跨调用追踪及指代解析。
2. 当前任务目标、约束、澄清答案的显式更新。
3. 最近原文、任务状态、相关历史的分层上下文。
4. 带来源的分块检索、事实记录及新旧信息处理。
5. 结构化接口与程序校验。
6. 纠错过程中的失败记录和重复失败检测。
7. 离线协议测试、真实模型任务评测及消融实验。

必须保持：

- 当前用户明确要求优先于历史推断；用户／项目范围隔离继续生效。
- 模型方案、用户报告、实际执行、实际产物验证分别记录。
- 历史审批不能授权新动作。所有执行继续遵循现有审查及人工确认流程。
- 命令、起始目录或 Shell 改变后，清除旧审查及审批身份，重新审查和确认。
- `interrupt()` 所在节点不加入模型调用或执行副作用，避免恢复时重复操作。
- 记忆或状态写入失败不能触发命令重放，不能把已经完成的文件操作改写成未执行。
- 原始日志保留，摘要和结构化状态可追溯；reasoning 不自动进入对话历史或事实库。
- 固定模型、采样、reasoning 和预算做对比；单独改变这些参数时作为独立实验报告。

首轮不包含模型训练、默认模型升级、任意 Bash 的自动语义解析、完整自动回滚、任意外部文件移动追踪或跨进程审批恢复。新的多轮能力先显式启用；实验开关关闭时应保持旧路径。

## 4. P0：对象状态及执行证据

### 4.1 目标与最小场景

同一用户和项目中，执行三次独立调用：

1. “创建 notes.txt，内容为 alpha。”
2. “把刚才的文件重命名为 todo.txt。”
3. “给刚才的文件追加一行 beta。”

系统应追踪同一个文件对象的路径变化。最终 `todo.txt` 内容满足约定，`notes.txt` 不再存在，无关文件不变。第三轮不能要求用户重新提供已经有明确证据的文件名。

### 4.2 建议的数据设计

以下字段为建议模型，可按项目风格实现为 dataclass／TypedDict／Pydantic 和 SQLite 表；具体类名由实施 agent 决定。

| 记录 | 最小字段 |
| --- | --- |
| 对象 | `entity_id`、`user_id`、`project_id`、`kind`、`current_path`、`status`、`version` |
| 对象事件 | `event_id`、`entity_id`、`operation_id`、`operation_kind`、旧／新路径、时间、执行状态、验证状态 |
| 来源 | 原始日志 `session_id`、事件 ID 或操作 ID、来源类型 |
| 最近关注对象 | 对象 ID、产生关注的用户轮次及来源；按用户／项目隔离 |

路径存储应保留实际执行时的绝对路径及起始目录；不用当前调用目录重新解释旧的相对路径。对象身份不能仅由路径决定：文件被删除后在同一路径重新创建，不应无条件沿用旧对象 ID。复制产生新对象；重命名／移动在有证据时更新同一对象；删除保留 tombstone，停止把它作为可操作的现存文件返回。

### 4.3 如何产生可信更新

- 模型可以提出目标对象及预期操作，但不能直接宣称操作已完成。
- P0 只覆盖受控的创建、重命名、追加场景。为这些操作定义明确的对象和预期效果数据，绑定到待审查的实际命令及动作身份。
- 不能因为自然语言计划提到了路径，或整批命令返回成功，就自动确认所有计划产物。采用只读、程序定义的产物检查，记录实际检查条件和结果。
- 验证器不得自动执行模型生成的任意验证 Shell。对已解析、限定范围的路径使用受控检查，并写入日志。
- 不凭文件名相似性认定任意 Bash 已完成重命名。无法建立操作与执行证据对应关系时，保留为未知／未验证状态，走澄清或重新检查。
- 整批命令失败可能已有部分效果。仅记录检查到的事实；未检查部分保持未知，纠错前重新观察，避免重复追加或重复创建。
- 不把简单存在性检查当成所有操作的充分证据。创建需要检查目标类型／约定内容；追加需要检查预期内容；重命名需要检查旧路径与新路径及足以关联对象的证据。记录验证能力的边界。
- 原始执行日志先持久化，再提交对象更新；更新键应幂等，例如由来源操作 ID 和效果编号组成。写入中断后的恢复只能重建状态或重做只读验证，不得重放文件操作。

可以新增专门的对象状态模块／存储，并在 `workflow.py` 和 `samantha.py` 接入。保持现有 `MemoryBackend` 的原始历史职责，避免把任何后端都强制变成对象数据库。

### 4.4 指代及持久化规则

- 对“刚才的文件”“它”等表达，先查询当前任务对象与项目最近关注对象，再补充相关历史证据。
- 唯一且有明确语境的候选可用于解析；多个同等合理候选应提出聚焦的澄清问题，不能只因为某个文件最新就强行选择。
- 用户明确指定目标时使用该目标，不被历史对象覆盖。若用户明确指向旧路径，检查实际环境；不能擅自替换成新路径。
- 已知重命名后的旧名称可作为同一对象的历史线索，但操作使用已验证当前路径。
- 路径可能被外部改变。使用前进行受控检查；缺失时标记状态过期，澄清或重新定位，不能自动创建替代文件掩盖缺失。
- 使用与 `MemoryScope` 一致的稳定用户／项目范围。项目 ID 需在项目内目录切换后仍可保持一致，显式配置优先；不扩大到其他项目。
- 跨调用保存对象状态，不恢复旧的 `approved`、`commands` 或审批身份。每次调用仍建立新的日志会话和工作流线程。
- SQLite 更新需事务化、幂等，并处理并发调用的版本冲突；禁止较旧的写入覆盖较新的已验证路径。

## 5. P1：任务槽位、结构化更新及消歧

在现有 `SamanthaState` 旁扩展当前任务信息，不用一段不断增长的自然语言摘要承担全部状态管理。

建议保存：目标、操作类型、对象引用、参数、用户约束、缺失参数、澄清问答、任务版本、每个字段的来源。文件名、内容、输出格式、是否留在目标目录等可作为具体槽位。

更新规则：

1. 原始输入及原始澄清答案保留；短回复结合前一个问题解释。
2. 同一任务字段被当前用户明确更正时产生新版本，并使被替代值不再作为当前要求；其他未改动约束保留。
3. 历史偏好只在适用范围内补充缺失信息，不能覆盖当前明确要求。不同对象、不同项目或不同适用时间的事实不能简单按“最新一条”合并。
4. 用户说“取消”后结束当前任务；旧计划及其目标信息不得自动成为下一轮待执行动作。
5. 有多个对象或冲突来源时，输出待澄清事项；不使用模型自报置信度作为唯一执行依据。

结构化输出应明确区分“补充字段”“更正字段”“仍缺信息”“取消任务”。先扩展现有澄清 schema 和校验，逐步将计划中的目标对象、操作类型及参数结构化，保持现有服务接口的兼容边界。不要一次强制所有角色迁移到同一个复杂 schema。

程序校验至少包括必填项、枚举、类型、引用对象属于当前范围、字段更新来源存在、取消状态不携带可执行动作。有效 JSON 不能代替语义校验和产物验证。格式错误继续遵循有界失败处理；若增加格式修复，限制次数并记录额外调用，修复不得执行命令或更新已完成事实。

验收场景：

- 已回答文件名后，不再用另一种措辞询问同一文件名。
- 用户从 TXT 改成 CSV 后，保留其他约束并更新格式。
- 两个候选文件下的“它”需要一次明确消歧；唯一有证据的候选避免无必要澄清。
- 当前明确路径优先于历史路径；取消后重新开始不会恢复旧动作。

## 6. P2：分层、分角色上下文

增加统一的上下文组装层，将上下文选择与各 agent 的提示词解耦。保留现有提示词职责，避免每个角色自行加载整份历史。

每次模型调用按需要选择：

1. 当前用户输入及必要的最近原文问答。
2. 当前任务目标、有效约束、缺失字段和已解析对象。
3. 当前相关的执行／验证结果及失败记录。
4. 有来源的历史片段或事实。

固定系统指令继续放在指令通道。历史日志、检索内容和摘要明确标记为参考证据；其中出现的指令文本不能获得执行授权。

| 角色 | 重点信息 |
| --- | --- |
| 澄清 | 当前请求、原始问答、有效槽位、候选对象、缺失或冲突信息 |
| 意图解析 | 已澄清任务、约束、解析后的目标对象、必要环境信息 |
| 命令生成 | 当前结构化计划、确切路径／目录、有效约束、有关的已尝试方案 |
| 命令审查 | 原始及澄清后的请求、计划、实际命令、起始目录、Shell、相关证据和上次错误 |
| 纠错 | 原目标和约束、已执行动作、观察到的部分效果、错误及已尝试方案 |

预算要求：

- 当前原始要求、关键澄清和审批所需的实际命令不能被历史挤出；必需内容本身超过预算时报告问题或使用明确的有界处理，不静默丢弃。
- 最近原文窗口、每条历史上限、来源数量和各层预算作为可配置参数，用开发集选择。窗口大小按实验确定，不在此写死为“最优轮数”。
- 当前 `MemoryQuery.max_chars` 及 `SAMANTHA_MEMORY_BUDGET` 是字符预算。新增 token 预算时须显式命名并使用相应 tokenizer／模板，不能把字符数当成 token 数。
- 总输入预算还应包含系统提示、消息模板和输出预留；核对实际 Ollama 上下文配置，不仅检查模型宣称的窗口上限。
- 保存所选来源、被截断内容、预算单位和上下文组装版本；避免把同一澄清答案同时重复塞入历史、包装输入和摘要。
- 摘要保留未解决事项、约束及来源，原始日志可回查。压缩不得把推测或模型计划转换为观察事实。

重新检索在补充关键槽位、明确对象或修改任务之后发生，并记录触发原因；设定次数／成本上限，避免每个节点无条件重新检索。任务信息改变后不能一直沿用第一轮的过期检索结果。

验收：插入长篇无关历史后，明确约束和对象仍保留；不同角色获得预期信息；预算及截断日志可检查；关闭该功能可回到原路径。

## 7. P3：分块检索及带来源的事实更新

### 7.1 先改分块与装包，再比较事实提取

保留 `none`、`recent`、`bm25` 原始行为和实验标识，新增策略采用独立名称／版本。复用 `MemoryBackend` 的适配边界，避免将某个记忆框架耦合到所有 agent。

第一步把长会话按消息组或事件／操作组切分，保留原始会话 ID、范围、时间和消息／事件位置。分块不能丢掉必要的问答、执行动作与结果关联。词法查询可结合当前请求、已确定槽位和对象名称；明确原始查询与扩展查询，保留诊断输出。

对召回片段去重、按相关性与来源分配预算，设置每段上限，避免首段填满全部预算。更新类问题要保留相关旧值和更正证据；多会话问题要覆盖必要来源。具体选择策略在开发集比较，不能为了指标机械要求每个会话都占一个位置。

当前实验记录的 BM25 来源会话召回 53.93% 等数据只代表来源 ID 覆盖，不代表答案正确率，也不保证截断后的文本含有答案。新策略应检查实际证据内容，再使用固定 reader 做 QA。

### 7.2 事实提取是后续独立策略

事实记录至少包含主体、属性、值、适用范围、来源类型、原始来源 ID／位置、记录时间、已知有效时间和状态（有效／已替代／冲突／待验证）。没有有效时间证据时保持未知，不凭空构造时间。

- 用户自述、偏好、模型计划、执行观察和验证事实采用不同类型。
- 合并后保留全部贡献来源；检索遵守 `as_of`，不能带入未来来源。
- 同一属性被明确更正时标记旧值已替代，保留可追踪历史。
- 文件存在与路径属于易变环境状态，依赖检查及对象事件；不能作为永久事实。
- 摘要／事实提取发生错误时不覆盖原始数据。需要额外模型调用时记录模型、提示词版本、耗时和失败。
- 基准数据的答案、题型和证据标签不能进入提取或检索输入，继续遵守现有评测隔离协议。

首轮可同步处理少量数据。若引入后台提取，使用可恢复的持久任务队列，不依赖 CLI 退出后仍运行的内存线程。向量检索、外部记忆库或重排模型在明确瓶颈和对比结果后再单独引入。

验收：小预算下覆盖多个实际证据片段；更正、无答案、时间截止和项目隔离正确；重复摄入幂等；分块及事实来源可回到原文；实际 QA 与终端任务结果分别报告。

## 8. P4：失败记录及重复失败检测

增加尝试记录：任务版本、实际命令、动作身份、起始目录、错误类别、错误摘要、已观察效果、纠错方案和来源操作 ID。原始错误留在日志，传给模型的错误文本按预算选择。

优先记录可从执行器取得的退出码及结构化结果；兼容当前 `ExecutionResult` 和 `WorkflowServices` 注入边界。错误分类不能只依赖模型判断，无法确定时使用 `unknown`。

同一任务版本及起始目录中，检测连续的同一动作／同一错误。不要随意重写 Shell 字符串来“规范化”命令，以免改变引号或语义。重复动作且没有新证据或环境变化时，要求不同方案、必要澄清或有解释地终止；如果增加新路由，仍保持既有审批与次数上限。

纠错前检查可能已完成的效果，尤其是非幂等追加。新方案包含变化后的命令必须重新审查和确认。默认三次纠错上限继续保留；历史类似失败只作参考，不据此断言当前环境相同。

验收：完全重复的失败动作被检测；新的方案不会因相似错误被误拦；部分完成后不会重复追加；取消、次数耗尽和每轮审批行为正确。

### 9.2 真实模型任务

复用现有 6 个记忆场景和 25 个真实任务，新增以下情况；沿用 task catalog 的版本规则，保持旧用例可复现：

| 场景 | 主要断言 |
| --- | --- |
| 创建→重命名→追加，三次独立调用 | 当前路径及最终文件字节正确，旧路径不存在 |
| 多候选对象指代 | 需要消歧时问一次聚焦问题，无擅自操作 |
| 用户更正目标／格式 | 最新明确字段生效，其他约束保留 |

| 失败前已有部分效果 | 只记录已验证效果，不重复非幂等操作 |
| 长篇无关历史 | 保留当前约束及必要证据 |
| 跨用户／跨项目 | 无对象和历史串用 |

### 9.3 指标及消融

固定模型、模型版本／可取得的 digest、量化配置、运行环境、采样参数、reasoning、上下文配置、数据版本、预算和任务集合。记录代码版本与 dirty 状态、实验开关、reader／judge、上下文组装及提取版本。

顺序比较原始基线、加对象状态、加任务槽位、加上下文组装、加分块检索、加事实提取、加失败记录；保留必要的单项消融，避免同时变更多个机制后无法判断收益。

指标至少包括：

- 多轮任务最终成功率，以实际文件及状态断言为准；保留失败和错误分母。
- 指代解析、更正后的约束遵守率，以及需要消歧时正确提问的比例。
- 不必要澄清次数，同时记录缺少必要澄清的错误，不能仅追求少提问。
- 虚假完成／陈旧路径使用、重复失败／重复副作用、状态持久化错误。
- 端到端及各阶段延迟、模型调用次数、实际可取得的 token 用量；不能将字符数冒充 token。
- 审批违规及范围泄漏。离线回归应零违规；真实评测发现违规时暂停该实验发布并修复。

小模型输出有波动，对关键用例重复运行并报告次数、成功／失败数量及延迟分布。参数在开发集选择，测试集不反向用于训练或调参。

LongMemEval 沿用现有 runner 和官方 judge 协议；oracle 用于区分 reader 问题与检索问题，不能与 cleaned S 混报。来源召回、QA 正确率、Samantha 终端成功率分别报告。公开 QA judge 的外部调用按当前仓库配置和授权执行，不默默启用外部模型或 Azure fallback。

thinking 与 non-thinking 的比较可作为独立后续实验。先保留当前配置，不在状态／检索改动中同时调整；简单澄清和复杂纠错可以分别测量质量、延迟和成本，不能假定打开 thinking 必然改善。
